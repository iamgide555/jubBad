# Advanced Early Checkout Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Freeze and share an early leaver's bill while keeping later games, reusable shuttles, and the final bill financially honest.

**Architecture:** Advanced sessions persist a checkout ledger separately from transient roster rest state. A server-calculated preview carries a snapshot token; confirmation rechecks it and atomically freezes the amount, marks the player unavailable, and credits later bills. The pure bill engine gains a fourth `perShuttle` model and residual-cost allocation; the host UI shows preview, settlement, undo, and a final bill divided into settled and still-due people.

**Tech Stack:** Dependency-free TypeScript billing (`node:test`), NestJS/Prisma/SQLite (Vitest), Angular standalone components/signals (`ng test`).

**Spec:** `docs/superpowers/specs/2026-09-30-early-checkout-design.md`

## Global Constraints

- Implement feedback A and D before executing this plan: D supplies `Session.shuttleToolsEnabled`, session shuttle IDs/use logs and consistent bill reads. E and `perShuttle` are available **only** on sessions whose snapshotted switch is true. F remains always configurable and independent.
- Early model choices: `perGame`, `perShuttle`, `buffet` only; final model choices on advanced sessions: `fair`, `perGame`, `perShuttle`, `buffet`. Ordinary sessions keep three models and cannot inherit `perShuttle`.
- `perShuttle` base is session `startingFeeSatang` plus the player's share of **recorded distinct identities**, priced with existing `Session.shuttlePriceSatang`. Never scale this model to optional physical `shuttleCount`. Zero price/count is valid; unknown game use is not zero.
- Preview/copy does not settle or disable. Explicit confirmation freezes amount and breakdown; undo requires confirmation, is allowed only before session end, and leaves an auditable undone record. No normal roster toggle can reactivate a settled leaver.
- Checkout refuses players on pending/active courts; the host clears pending manually or finishes/abandons active. Confirm uses the same per-session lock and a DB transaction for preview revalidation, ledger write, and roster update. Repeated idempotency keys never create a second charge.
- Frozen payments are credited against final `fair` cost or final `perShuttle` recorded-shuttle cost; final price-based per-game/buffet rates for other people are unchanged. No negative still-due amount: excess credit is an explicit refund warning, uncovered cost an explicit shortfall. Later reuse/corrections never rewrite a receipt.
- Walk-in surcharges remain a group discount, overrides bypass them, and later surcharges cannot rewrite early receipts. Thai-primary/English UI, 44px host controls, always-Thai LINE copy, ownership mismatch 404 and no public checkout data.

## Review Focus

1. Two concurrent settle requests for one player with different idempotency keys must leave one active receipt and one inactive roster row (Task 4).
2. A physical shuttle used by game A before checkout and game B afterward must still be charged only once, with the settled player's amount unchanged (Tasks 3 and 5).
3. Switching a group off after an advanced session must not strand its checkout, while a new ordinary session cannot inherit `perShuttle` from that advanced bill (Tasks 1 and 7).
4. A pending proposal formed just before checkout must block settlement without changing its lineup, even if auto-confirm is queued; after settlement, reactivation/manual seating must be refused (Task 4).
5. A post-checkout correction reducing cost below settled amounts must show an excess/refund without negative rows or a falsely reconciled copy (Tasks 5 and 8).
