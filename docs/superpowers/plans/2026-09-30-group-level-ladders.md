# Group-Owned Level Ladders Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let each group's host configure ordered skill levels and starting Elo without changing ratings earned before a ladder edit.

**Architecture:** Persist an optional ordered group ladder and a frozen rating seed per player. A protected, revision-checked group editor serializes ladder changes with session creation and level assignments; engine pairing receives the group ladder explicitly. Host pickers read the same protected configuration while public responses remain level-free.

**Tech Stack:** Pure TypeScript engines (`node:test`), NestJS/Prisma/SQLite (Vitest), Angular standalone components/signals (`ng test`).

**Spec:** `docs/superpowers/specs/2026-09-30-group-level-ladders-design.md`

## Global Constraints

- Existing groups stay on BG, N, S, P-, P, P+, C, B with seeds 900 through 1600 until an explicit switch. F is available to **all** groups, independent of D/E's advanced-tools setting.
- First standard-to-custom switch and custom-to-standard reset clear **labels only**; saved rating seeds, timestamps, match history and both rating tracks remain unchanged. Within custom, rename migrates labels; reorder/seed edits do not reanchor players; in-use removal fails. A level-bearing write carries the ladder revision; a stale tab must not reapply a cleared label even when the new ladder reuses that name.
- No ladder edit while **any** session in the group has `endedAt=null`. Assignment during a session remains allowed. Owner mismatch is 404; levels are absent from public endpoints.
- Custom ladder: 1–16 short Unicode names (trimmed, <=16 code points, unique case-insensitively), non-negative integer strictly increasing Elo seeds; offer centered 100-point gaps around 1200. A moved level keeps its ID/name/seed.
- Preserve wait-only level rotation, ±1 level band, carry-game rules, session-independent court rotation, default pairing behavior, and the rule that a deliberate player level change resets the rating anchor at that moment.
- Read `docs/overview.md`, the F spec and the shipped A/C/D/E interfaces before execution; preserve unrelated dirty work, and do not implement F until the user explicitly chooses execution after all feedback plans are reviewed.

## Review Focus

1. Swapping the names of two **existing IDs** in one edit must migrate both groups of assigned players without losing one name or reanchoring Elo (Task 3).
2. A session being created while a host saves a ladder must either finish first and block the save, or see the new ladder; never start with a partly cleared roster (Task 3).
3. A player with `levelSetAt=null` and old BG/P seed, plus a previously cleared player with a timed 1200 anchor, must retain the same singles/doubles replay after the first custom switch and reset (Tasks 2–3).
4. A stale browser's old `N` assignment after switching to a custom ladder **also named `N`** must be rejected by revision, including inside session creation or walk-in, with no partial player/session row (Task 4).
5. A one-level ladder and a group whose level is invalid in persisted data must never produce a negative index or silently treat corruption as an untagged player; ordinary default-group pairing remains unchanged (Tasks 1 and 5).

## File map

- `engines/levels.ts` defines ladder validation, defaults, seed and dynamic ordering/band/carry helpers; `engines/pairing.ts` consumes an explicit ladder in every level-aware search path. Neither knows about database JSON or Angular.
- `server/prisma/schema.prisma` and one migration hold the group list/revision and frozen player seed. `server/src/groups/group-levels.ts` parses persisted JSON and maps revisioned drafts; `group-levels.service.ts` owns group serialization, editor operations and contextual level lookup. `server/src/player-levels.ts` owns per-player anchor reads/writes.
- `GroupsController` exposes owner-only ladder GET/PUT; `GroupsService`, `SessionsService` and their DTOs validate every assignment against the owning ladder. `web/src/app/core/group-levels.model.ts` plus `RosterService` transport the owner-only data; a group-level settings page edits it. Existing `LevelPicker` and the four host flows consume that data.
